# Instagram Reels and video gallery feasibility

Research date: October 22, 2026. Planning only. No account connected, app created, token obtained, CMS changed, video uploaded, or integration implemented.

## Recommendation

**Short term:** publish a curated collection of six videos, managed in Sanity, using Emily's original website-cleared exports and locally controlled cover images. Deliver small optimized MP4s from Cloudflare R2, with one click-to-play player. If originals cannot be supplied, use curated public Reel links and official embeds loaded only on request, with a permanent external-link fallback. The latter has less control over performance, privacy, and playback availability.

**Long term:** add official API discovery to that curated gallery, with a scheduled Cloudflare Worker, persistent last-good metadata, and a Sanity approval/override layer. Start the capability pilot with **Instagram API with Unified Login**, which Meta now recommends for new integrations. Keep stable approved originals as the reliable playback layer and use official embeds/links when API media is unavailable. Do not promise that every newly posted Reel can automatically play as a native website video.

Automatic discovery of an authorized professional account's posts is realistic. Automatically showing the six newest **eligible, approved** Reels is achievable after validating the account, API fields, and publishing policy. Unconditional playback of the six newest Reels is not a reliable promise: licensed music can remove the video URL from API responses, posts can become unavailable, and provider embeds can be blocked or require further interaction.

Emily must have a **Business or Creator professional account** for the authenticated media API. A personal account is not sufficient. Either professional type can support this use; do not recommend switching account type merely to broaden a music library. Public individual embeds have different requirements: public content, embedding enabled, and an available/non-restricted post.

This gallery needs only media reading. During the pilot, verify whether an Instagram-compatible configuration can be reduced to the necessary access. Do not silently enable messaging, publishing, or advertising just to make a feed work. For an owner/managed-account-only integration, Meta's overview allows Standard Access when the account/people have the appropriate app roles. Advanced Access is required to serve other accounts without those roles; that requires App Review and business verification, and applicable live-mode setup. Do not promise approval or treat an arbitrary developer test token as a production integration. Confirm Emily's ownership/roles in the actual dashboard. Business-portfolio ownership and business verification are different requirements. [Access levels](https://developers.facebook.com/documentation/instagram-platform/overview), [Unified eligibility](https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-unified-login/eligibility-and-troubleshooting).

OAuth, if implemented, belongs in an owner/admin connection flow, not the bridal inquiry flow. Use a controlled HTTPS callback, server-validated `state`, exact registered redirect, and server-side code exchange. Visitors should never log into Instagram to browse Emily's website as a condition imposed by our gallery. A provider embed may independently present its own login restrictions; retain an alternative.

### Token expiration and renewal

- **Unified:** expiration is chosen in the login configuration. Store the token with `client_business_id`, Instagram account IDs, and `config_id`; inspect the selected expiry. The business integration token management API can manage/refresh it and requires `business_management` access for that management feature. Do not add that broad scope without evaluating the need. Tokens can stop working when the app is removed or the Instagram asset changes portfolio. `/me` represents the integration user; obtain account IDs from `/me/assigned_instagram_accounts`. Do not apply Instagram Login's refresh endpoint to this token type. [Unified authentication](https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-unified-login/authentication).
- **Instagram Login:** OAuth's short-lived token lasts one hour; a long-lived token lasts 60 days. Refresh an unexpired long-lived token once it is at least 24 hours old; the refresh gives another 60 days. Schedule renewal around day 30 and alert well before expiry. An already expired token needs reconnection; no perpetual-token promise. [Business Login lifecycle](https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-instagram-login/business-login), [refresh reference](https://developers.facebook.com/documentation/instagram-platform/reference/refresh_access_token).
- **Facebook Login:** follow that route's actual User/Page-token and data-access expiration rules. Some Page-token configurations have no scheduled expiry, but permissions/removal/security changes can still invalidate them. Verify returned expiry and reconnection requirements; never label them permanently valid.

Tokens/app secrets remain server-side, outside `PUBLIC_*` variables, client bundles, repositories, CMS public documents, URLs, analytics, and logs. A refreshed token must be written to a server-only secure persistent store; changing a local in-memory variable does not rotate a deployed secret. Define the operator and storage mechanism during implementation.

## Discovery, fields, and the important media limitations

Use the authorized Instagram account ID to enumerate its `/media` edge. Request only necessary supported fields, page through a bounded set of results, deduplicate by ID, and sort by `timestamp` ourselves. Filter **before** selecting six; six returned media objects are not necessarily six Reels. Mixed photos/carousels, collaborators' posts, deletions, and older pinned content must not silently distort the list.

The media reference provides `id`, `media_type`, `permalink`, `timestamp`, video `thumbnail_url`, and optional `media_url`. Crucially, it currently marks **`media_product_type` as available for Facebook Login only**, and the same restriction appears on `caption`. Therefore do not ship a generic `VIDEO && media_product_type === REELS` query under Instagram Login or assume every video is a Reel. The newly recommended Unified route and its specific Reel-identification behavior require an account capability test; shared permissions/host do not prove every field's availability. If exact automated Reel-only classification is unavailable, retain confirmed Reel IDs/curation, validate supported permalink identification, or use a verified Page-linked route if Emily already maintains one. This limitation is part of the pilot, not hidden implementation work. [Current IG Media reference](https://developers.facebook.com/documentation/instagram-platform/reference/instagram-media).

**Licensed audio is a material blocker to automatic native playback.** The October 20 media reference says `media_url` can be omitted for copyrighted/licensed audio, including Instagram's audio library, even for media the app user owns. It also describes additional download-setting restrictions for reading other users' Reels. `media_url` must be optional. An API token does not fix absent media or establish permission to republish music. Use Emily's cleared original export, an official embed, or a permalink fallback. Do not extract video files from embed HTML or use a downloader to replace a denied field. [IG Media restrictions](https://developers.facebook.com/documentation/instagram-platform/reference/instagram-media).

CDN media/poster URLs are not durable asset identifiers. Meta describes them as privacy-aware: deletion/expiry can stop access. No fixed lifetime is promised here. Store the ID and permalink, refresh authorized URLs, and never compile an expiring video URL into static HTML indefinitely. Stale thumbnails should not survive source deletion/revocation unchecked. Owner-supplied originals with independent publication permission are a separate asset collection. [CDN behavior](https://developers.facebook.com/documentation/instagram-platform/overview).

## Embeds and current oEmbed behavior

The current [official embed guide](https://developers.facebook.com/documentation/instagram-platform/oembed) supports public photos, videos/Reels and feed content, excluding private/inactive/age-restricted accounts or embedding-disabled content. It shows a v26.0 `instagram_oembed?url=...` request without a token and documents 1,000 requests/hour. Older instructions requiring the former oEmbed Read feature/App Review should not be presented as a verified current requirement for manually selected embeds. Actual successful embedding still needs testing against Emily's chosen public links.

oEmbed renders a known URL; it does not discover the latest six Reels. Its returned HTML uses Instagram's embed library, initialized after activation. The output is a provider-controlled card whose dimensions vary; a 9:16 poster grid does not imply a raw 9:16 iframe with no Instagram chrome. Do not clip controls/branding to force that appearance. The guide restricts using oEmbed data for purposes other than front-end embedding; it is not a sanctioned thumbnail-extraction, media-download, or content-archival API.

Load the embed script once, only after explicit user activation and any required consent. The cross-origin frame cannot be restyled or controlled internally, and parent scripts cannot guarantee its play state, remove its login prompts, or inspect its contents. CSP/frame policies, privacy extensions, blocked cookies, regional restrictions, and changes to the source post can prevent playback. Do not bypass them. Provide a plainly labeled Instagram link and a useful photo gallery even when no embed works.

## Proposed Cloudflare/Sanity architecture

The repository currently prerenders pages; there is no scheduled backend for this feature. Keep that foundation and add only the small integration needed after approval.

1. **Owner connection:** authorized professional account → server-only OAuth/dashboard onboarding → secure token/expiry/account record. Verify actual fields using six representative posts, including a music Reel and an unavailable-post case.
2. **Scheduled discovery:** a separate Worker Cron job runs roughly every six hours, independent of website traffic. Enumerate a bounded recent window; filter confirmed Reels and sort timestamps. Use hourly discovery only if Emily needs that freshness. Polling is sufficient; do not assume a generic new-Reel webhook exists for every login setup.
3. **Normalization and curation:** upsert candidate records by media ID. Retain explicit exclude/pin/approval choices. Initially import new candidates as unresolved for Emily to select; if she later authorizes automatic publication, apply a clear eligibility rule and offer an override. “Newest approved work” is truthful language for the default experience; “latest Reels” is appropriate only for the genuinely automatic list.
4. **Playback selection:** stable original file when supplied/cleared; otherwise currently available API media only after permitted-use validation; otherwise official embed on activation; otherwise Instagram link. Do not automatically archive every Instagram binary to R2. Rights, Meta retention rules, and source removal handling must be verified before any authorized ingest.
5. **Public delivery:** keep the curated original gallery in static Astro HTML via Sanity/build publishing. If automatic current API URLs are needed, expose a small cached same-origin endpoint containing public-safe gallery data only. Prefer persistent KV/R2 metadata for last-good state and edge caching for delivery; do not use edge cache as the only durable store. Never expose the token or upstream paging URLs containing credentials.
6. **Failure handling:** transient API errors keep the approved gallery/posters and pause refresh with backoff; missing URLs use fallback playback; invalid permissions/tokens stop retries and flag reconnect to the operator. Expired upstream URLs trigger one bounded server-side refresh, not browser retry loops. Deletion or revoked publication removes the associated Instagram-derived entry on reconciliation. A broken API must not break Home or HoneyBook.

Cloudflare Workers can make HTTPS API calls and run scheduled jobs. R2 is suitable for stable original files; use a production custom domain and correct content type/cache headers, byte-range handling, and CORS for captions where needed. Do not proxy/transcode entire videos in Worker memory. Stream supplies managed encoding/adaptive delivery if actual usage or file sizes justify it. [Workers Cron](https://developers.cloudflare.com/workers/configuration/cron-triggers/), [R2 public delivery](https://developers.cloudflare.com/r2/buckets/public-buckets/).

Proposed Sanity fields: title, poster with alt/hotspot, source permalink/media ID, display mode (`ownedVideo`, `instagramEmbed`, `link`), original file/Stream ID, transcript/description, caption track, published timestamp, source/rights confirmation, approval status, active/featured, display order and sync status. Store API credentials elsewhere. Reuse `OWNER_APPROVED` and permission conventions; adding a second ungated media system would weaken the current architecture.

### Rate limits and caching

Do not rely on the common but overgeneralized “200 calls/hour” claim. The current Platform overview describes Business Use Case limits and an impression-based rolling 24-hour budget for non-messaging endpoints; exact effective capacity depends on the app/account. Inspect actual usage headers and 429 responses during the pilot. The separate oEmbed guide documents 1,000 requests/hour. Six-hour discovery is roughly four cycles/day before pagination/details, so this site should not need visitor-driven API calls. [Platform rate model](https://developers.facebook.com/documentation/instagram-platform/overview).

Proposed operating targets: six-hour metadata refresh, cached public manifest, persistent last-good approved collection, explicit source revalidation, exponential backoff, and operator alerts after repeated failures or when expiry approaches. Cache policy must respect source availability and Meta terms; “last good” is not permission to retain deleted content indefinitely.

## Actual section layout and interaction

- **Placement:** after the immediate photo gallery and one-sentence introduction, before compact packages. Finished still photography establishes style first.
- **Six items:** enough range for two desktop rows without becoming an endless social feed. If only three rights-cleared clips exist, launch three instead of duplicate placeholders.
- **1440px:** three columns/two rows, within the existing wide content bounds. **768/390px:** two columns/three rows. **320px:** one column so posters/controls remain usable. Do not hide the last three clips with no discoverable control.
- **Poster:** consistent 9:16 window; hair remains in-frame. For nonvertical video, use a suitable cover but preserve the actual video's proportions in the player rather than cropping away technique.
- **Activation:** a real button labeled with the look, e.g. “Play textured updo video.” Load no MP4 source or Instagram script before activation. Use a lightweight responsive dialog with one player, native controls, `playsinline`, a close action, keyboard focus management, Escape and focus restoration. Pause/unmount on close. Use an inline player instead if a modal cannot be made accessible; an Instagram embed must have enough width and height for all controls.
- **Audio:** never autoplay with sound. Show understandable silent previews/covers; speech/instructions need synchronized captions. Include a concise description of visual-only technique/result and accessible equivalent information where necessary. A poster alt alone does not describe a whole video. [W3C media accessibility](https://www.w3.org/WAI/media/av/).
- **Fallback:** short unavailable message and “View on Instagram” link, without endless loading. Add one verified “View more on Instagram” section link. Browsing the static portfolio remains useful if the visitor declines third-party content.

Poster-only loading avoids six concurrent media downloads and third-party players. Reserve image/player dimensions to protect CLS, keep the hero separate from the video script, and test slow mobile networks. `preload=none` is helpful, but withholding `src` until activation gives more reliable control over initial requests. [Video loading guidance](https://web.dev/articles/lazy-loading-video).

## Privacy, rights, maintenance, and fallbacks

Owned poster/video delivery avoids loading Meta merely because someone visits Home. Activated embeds can send visitor connection data to Meta; the final Privacy text and consent behavior should describe the selected implementation. No legal compliance conclusion is made here. The existing HoneyBook privacy/provider notices remain in place.

Instagram's music availability is not evidence that Emily can export the same audio for a commercial website. Ask for originals with website-cleared audio or silent versions. Do not invent music licenses or client permissions. Meta's current media restrictions make this both a rights question and a technical availability issue. Consult the actual licenses and [Meta's music policy](https://www.facebook.com/legal/music_guidelines) before reusing audio; that policy URL was login-restricted in this session.

Assign a named technical operator. Check sync health automatically, review failures/expiry monthly, and review API/version changes periodically and before planned upgrades. Emily should be able to exclude a clip or replace its cover in Sanity without a code change. Test revoked access, 429s, empty feed, missing `media_url`, expired URL, deleted/private post, blocked embed script, mobile player sizing, keyboard dialog behavior, and caption availability. These are future acceptance cases; no integration tests were run for an unimplemented feature.
