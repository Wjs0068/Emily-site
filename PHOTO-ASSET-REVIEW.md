## Homepage photography plan

Aim for one finished-look hero plus six gallery photographs, one Emily portrait, and six distinct video posters. This is a placement target conditional on assets, not permission to repeat three images to fill six slots. Roughly five of the six static gallery slots should show completed hair clearly; a single wedding-day context image can provide atmosphere. Keep process photography out of this first gallery.

Use a restrained three-column/two-row portrait gallery at 1440px, two columns at 390px and 768px, and one column at 320px when detail becomes unreadable. Prefer 3:4 or 4:5 image windows; maintain natural head/hairstyle proportions. Use the 320px single-column exception to protect detail even if it adds page length. At 390px, the large hero supplies the immersive view while the six-picture grid supplies range. Offer an accessible larger view or a clear Portfolio link; essential looks must not be hidden behind hover or swipe.

Do not introduce an additional full-width photo break simply to increase image count. Add one only if a supplied landscape photograph justifies it and replaces an existing text block. Current sources are overwhelmingly portrait-oriented. A wide wedding photograph cannot automatically survive a 9:16 crop, and a tight updo portrait cannot automatically survive a full-width landscape crop.

Proposed first selection now that the files are present: new `rsz_img_9637.webp`, new `rsz_img_2432.webp`, IMG-04, clean/cropped IMG-08, and two of IMG-05 / new turning portrait / new reception view, chosen for variety after Emily confirms style/session overlap. Keep the horse and distant field photograph secondary. IMG-04 remains the most flexible existing high-resolution color hero source; the new monochrome rear view is a stronger hair-focused portrait candidate but needs a deliberate split layout and quality review. Do not repeat the hero in the first gallery if enough alternatives are approved.

## Portfolio evolution

Lead with finished hairstyles, followed by wedding-day context, with at most one small process image near the end. A target of 12–18 strong, distinct photographs is useful only if enough approved originals exist. The available eight fallback items should not be inflated with repeats or reference-site images.

Group work by High updos, Half-up, Waves, and Textured details where the actual library supports those distinctions. Texture can span several style types; propose tags rather than making it a mutually exclusive style category. Existing Sanity `styleCategory` has `updo`, `halfUp`, `down`, `short`, and `other`; a future subtype/tag field would be needed for high updos and texture. Do not add empty filter controls now. A short curated gallery needs no filtering JavaScript.

Use static responsive columns with consistent gutters, occasional larger context images, stable aspect ratios, and meaningful source order. Avoid reusing the current index-specific eight-item layout unchanged for a larger CMS collection. Supply hotspot/crop data to the renderer; the schema currently supports hotspots but the query/component do not apply them. Local imports already receive optimized Astro widths; the remote-image branch currently emits a plain image without responsive Sanity CDN URLs. These are implementation follow-ups, not completed features.
